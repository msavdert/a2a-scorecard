# Public A2A endpoint census, 2026-08-22

Session handoff note. Written to let a fresh session continue without
re-deriving any of this. Not an ADR: it records measurements and the
decisions taken from them, not architecture. Where it implies a change to
grading or probe semantics, that change still needs its own ADR per
CLAUDE.md rule 4.

## Why this was run

The v0.4 gate commits the project to a public scorecard. That plan rested on
an unvalidated assumption: that a public population of scannable A2A
endpoints exists at all. If most A2A deployments are enterprise, auth-gated
or inside private networks, a public scorecard has nothing to score. The
census was the cheap test of that assumption, run before spending v0.3 and
v0.4 effort.

Decision rule agreed before measuring:

- 500+ scannable endpoints: the scorecard thesis holds, plan the launch.
- 50-500: drop the scorecard, ship periodic ecosystem reports instead.
- Under 50: the scorecard is dead; retarget as a CI/conformance library.

## Method

1. Candidate discovery, no probing: agent-tools.cloud `/api/v1/resources/search`
   (paged, 2,258 records), a2aregistry.org API, awesome-a2a README, and GitHub
   code search. Merged and deduplicated to **2,542 candidate base URLs**.
2. Sampling: capped at 2 URLs per operator unit, then a seeded random draw of
   **400 targets across 396 operators**. The cap matters because six operators
   run 328 of the raw URLs as subdomain sprawl (hergertsynthora.com alone has
   120); without it the sample would describe those six, not the ecosystem.
   PaaS tenants (`*.vercel.app`, `*.workers.dev`, ...) count as their own
   operator, since each app is a distinct owner.
3. Scanning: the project's own scanner, concurrency across operators and
   strictly sequential within one, so no host ever saw two concurrent scans.
   That is what SCANNING-POLICY.md requires of batch mode. 400 targets in 65s.

Sampling rather than scanning all 2,542 was deliberate: each scan spends a
benign `SendMessage` ping that costs the target real compute, and the sample
answers the population question at roughly one sixth of the imposed load.

## Result: the population exists

- **310 of 400 (78%) are scannable** - reachable, with a fetchable agent card.
- 74 (18%) reachable with no card at either well-known path.
- 16 (4%) unreachable.
- Extrapolated over 1,807 operator units: roughly **1,400 live, publicly
  scannable A2A endpoints**.

That clears the 500 threshold, so **the scorecard thesis holds and the
project continues**.

Two caveats that belong in any public writeup:

- Selection bias upward. Most candidates came from a directory that already
  health-checks its listings, so 78% measures "agents a directory lists and
  keeps listing", not "all A2A deployments in the wild".
- The population is the indie/long-tail agent economy (x402 brokers, signal
  vendors, solo builders), not the enterprise adopters named in the
  Linux Foundation's 150+ organizations figure. Those remain behind auth and
  inside private networks and will not appear on a public scorecard.

## Result: the ecosystem is substantially non-conformant

Scannable population, n=310. Grades below are after correcting the C012
defect described in the next section.

| Measure | Result |
| --- | --- |
| Grade D | 199 (64%) |
| Grade A | 31 (10%) |
| Signed agent card (C031 pass) | 6 (2%) |
| Card declares v1 generation | 70 (23%) |
| Card only at legacy `/.well-known/agent.json` | 55 (18%) |
| Auth-gated at the protocol probe | 29 (9%) |
| TLS posture pass (C032) | 307 (99%) |

The dominant defect is C020: the agent's own declared endpoint does not
answer a spec-conformant JSON-RPC `SendMessage`. 193 of 310 fail it, 110 of
those by returning non-JSON. This was verified by hand against a real target
rather than trusted: `411data.io` publishes a card declaring
`url: https://411data.io`, and a JSON-RPC POST there returns an nginx
`405 Not Allowed` HTML page. Only 2 of the 110 non-JSON cases are explained
by MCP servers mis-filed as A2A in the source directory, so directory
contamination is not the cause. These failures are real target-side defects.

## Result: the competitor does not do conformance

agent-tools.cloud's headline count of 2,258 indexed A2A agents is **honest** -
paging its API returned exactly that many records. Its letter grade is not
conformance:

- The text rendered beside every grade-A row is literally
  `uptime_30d 1.0; p95 218.5ms`. The score is 30-day uptime plus p95 latency.
- Its detail API exposes `health`, `latency_ms`, `last_seen`, `confidence`
  and `conformance:"pass"`, with **no TLS field, no schema-validation result
  and no signature field**. Its own caption defines Conformant as
  "valid card + skills".
- `confidence` is a flat 0.6 on 2,122 of 2,258 records, i.e. a default rather
  than a measurement.
- 160 entries typed as A2A point at `/mcp` endpoints.
- No methodology page for A2A exists; `/about` documents MCP safety scanning.

So the differentiating claim is available and specific: **schema and protocol
conformance, TLS posture and card signatures - none of which any public A2A
directory currently measures.** Positioning as "SSL Labs for A2A" is weaker
than positioning against this gap directly.

Related context from the same research pass: the official project ships
`a2aproject/a2a-tck` (a self-run TCK) and `a2a-inspector` (a local debugger),
and has no public scorecard or badge programme. Cisco AI Defense ships an
open-source `a2a-scanner` (security-focused CLI/library, no hosted scorecard).
The nearest successful independent analogue is OpenSSF Scorecard, which is
foundation-adjacent rather than a lone operator.

## Defects found in our own scanner

### 1. C012 systematically emits false FAILs (blocking for launch)

`src/a2a_scorecard/checks/agent_card.py:83` `_detect_generation` classifies a
card as v0.x only when `url` is present **and** (`preferredTransport` or
`protocolVersion`) is present. A card carrying `url` but declaring no version
falls through to `unknown`, and C012 then validates it against the v1.0.1
schema, where top-level `url` no longer exists (v1 replaced
`url`/`preferredTransport`/`additionalInterfaces` with `supportedInterfaces`).
The card fails on a field that is correct for its actual generation.

Measured impact on the sample:

- 124 of 400 targets (31%) hit this path.
- 104 of those 124 have violations that name `url`, i.e. they are plainly
  v0.x-shaped cards.
- Correcting them from FAIL to SKIP changes 26 of 310 grades; F drops from 34
  to 16.
- No check declares `requires = ("C012",)`, so the defect does not cascade.
  The fix is local.

Why the test suite did not catch it: the conftest fake agent has no
version-silent card, so the fixture set never exercises the `unknown` branch.
Reality and fixtures diverged.

Intended fix: infer generation from card **structure** - `supportedInterfaces`
means v1, top-level `url` means v0.x - and when the generation genuinely
cannot be determined, SKIP the v1 schema check rather than FAIL it. Never let
a missing version declaration convert into a scored schema failure.

### 2. The scanner's User-Agent contact path 404s (blocking for public scanning)

`src/a2a_scorecard/__init__.py:5` advertises
`https://github.com/msavdert/a2a-scorecard`, which returns 404 because the
repository is private (CLAUDE.md rule 10). SCANNING-POLICY.md lines 16-18
require a **working** contact path. This was true for all 400 requests sent
during this census. Either the repo goes public before any public scanning,
or the User-Agent points somewhere reachable.

Also: `__version__` is still `0.1.0` although the v0.2 milestone closed, so
the version we present to targets is wrong.

### 3. Grade A is being earned on thin coverage (needs an ADR)

28 of the 31 A grades were computed over 110/160 or less of the rubric
(median 100/160). Because checks that do not apply are excluded from the
denominator, an agent on an older spec skips the hardest checks and scores
higher than a v1 agent that attempts them and drifts. **Being behind the spec
currently raises the grade.** ADR-0015's coverage reporting makes this
visible but the letter grade still says A. Publishing "A" next to a real
company's name while 37% of the rubric was never evaluated is not defensible;
this needs a grading ADR before launch.

## Task list for the next session

Ordered. Items 1-3 are launch blockers.

1. **Fix C012 generation inference.** Structure-based detection, SKIP on
   genuinely undetermined generation. Add regression fixtures built from real
   cards captured in this census (version-silent card with `url`; v1 card with
   `supportedInterfaces`; v1-declaring card that still carries `url`). Needs an
   ADR because it changes check semantics (rule 4). Re-run the census
   afterwards from the stored sample and diff the grade distribution.
2. **Fix the User-Agent contact path and version string.** Decide with the
   owner whether that means making the repo public or pointing at another
   reachable contact. Bump `__version__` to match the milestone.
3. **Write the grading ADR for coverage-versus-grade.** Options to weigh: a
   minimum-coverage floor below which no letter grade is published; publishing
   the grade only alongside coverage; or scoring un-evaluable weight as
   unearned rather than excluding it. Recommendation: do not publish a letter
   grade below some coverage floor.
4. **Enforce batch policy in the product, not just in the census harness.**
   `cli.py:54` scans multiple URLs in a plain list comprehension with no
   per-host serialisation, no pacing and no 429/Retry-After handling. The
   census harness in `research/census-2026-08-22/tools/runner.py` implements
   the correct shape and can be the model. Add integration tests for it.
5. **Design the v0.3 dataset schema (ADR).** Still the blocker it was before
   this session. It must carry `scanner_version`, `grading_version` and spec
   version per ADR-0011, and define what happens when a check is retired or a
   field is added. `data/census.jsonl` here is a first real corpus to design
   against rather than a hypothetical.
6. **Add a check-ID uniqueness guard to CI.** Rule 3 forbids reuse or
   renumbering and nothing currently enforces it.
7. **Consider publishing the ecosystem findings before the scorecard.** The
   headline is already defensible and needs no per-agent naming, so it carries
   far less risk than a scorecard: only 2% of public A2A agents serve a signed
   card, 23% are on v1, and roughly two thirds do not correctly answer at the
   endpoint their own card advertises. This builds standing ahead of launch.

Reproduce the summary with:

    uv run python research/census-2026-08-22/tools/analyze.py \
      research/census-2026-08-22/data/census.jsonl

Rescanning is not necessary to redo the analysis; `analyze.py` recomputes
outcomes from the stored per-check data rather than from the labels written at
capture time.

## Open questions

- Should the corpus be re-scanned on a schedule now, to start accumulating the
  time-series that ADR-0011 calls the primary long-term product? Doing so
  before the C012 fix would poison the series with known-wrong grades.
- Do we notify operators before publishing per-agent grades, and at what
  scale? v0.4 assumes pre-notification; at roughly 1,400 endpoints that is a
  real operational cost and needs a concrete plan.
- The 74 reachable-but-cardless hosts came from directories claiming they are
  A2A agents. Worth a separate look at whether the directories are wrong or
  the agents dropped their cards.
